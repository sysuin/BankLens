# BankLens

[![Live Demo](https://img.shields.io/badge/Live%20Demo-https%3A%2F%2Fbanklens.sysuin.com-blue?style=for-the-badge&logo=amazonaws)](https://banklens.sysuin.com)

**Live Web Application:** [https://banklens.sysuin.com](https://banklens.sysuin.com)

AI-powered bank statement analysis and banking product recommendation engine
built for bank Relationship Managers. Upload a statement as **CSV or PDF** and
BankLens returns a financial health report, a structured customer profile
generated by GPT-4o, and a two-product cross-sell pitch — every recommendation
grounded in a hybrid RAG pipeline over a curated banking product knowledge base.

---

## What it does

1. **Ingest** — a bank statement as CSV, or as a PDF from effectively any
   commercial bank, via a dual-engine pdfplumber parser
2. **Sanitize** — account numbers, card numbers, phone numbers, emails and
   PAN/SSN tokens are regex-masked *before* any text reaches an external LLM
3. **Categorize** — transactions are labelled by a two-stage hybrid engine:
   fast keyword rules first, then a batched LLM pass for anything unmatched
4. **Analyze** — income, expenses, savings rate and expense-to-income ratio are
   computed, and the credit risk band and health score are derived from them
   deterministically, not generated by a model
5. **Retrieve** — hybrid search (dense ChromaDB + sparse BM25, fused with
   Reciprocal Rank Fusion) assembles a wide candidate pool, which a reranker
   narrows to the passages that actually reach the LLM
6. **Profile** — GPT-4o writes the analysis, the two product recommendations
   and three RM call hooks, then output guardrails validate the products
   against the knowledge base before anything is displayed
7. **Display** — results are presented across three interactive Streamlit views

Every stage is covered by an evaluation suite: 65 golden cases run free on
every push, and a sampled paid layer scores retrieval quality and groundedness.

## Architecture

```
CSV / PDF Upload
    │
    ▼
[pdf_parser.py]    Dual-engine PDF extraction (table grid + date-block text)
    │              → normalized date, description, amount, type
    ▼
[sanitizer.py]     PII masking: account / card / phone / email / PAN / SSN
    │
    ▼
[categorizer.py]   Stage 1 keyword rules → Stage 2 batched gpt-4o-mini fallback
    │
    ▼
[analyzer.py]      Income, expenses, savings rate, expense ratio, top categories
    │              (internal Savings transfers excluded from expenses)
    │              Risk band + health score computed here, deterministically
    ▼
[rag.py]           Hybrid retrieval: ChromaDB dense + BM25 sparse → RRF fusion
    │              15 candidates
    ▼
[reranker.py]      Listwise rerank (or local cross-encoder) → top 4 passages
    │
    ▼
[agent.py]         LCEL chain: prompt + metrics + risk + context → GPT-4o
    │              → Pydantic + semantic guardrails + corrective retry
    ▼
[main.py]          Streamlit: Ledger view | Analytics view | AI Profiler view
```

The boundary between the deterministic and probabilistic halves is deliberate.
Anything derivable by arithmetic — the risk band, the health score, the deficit
flag — is computed in `analyzer.py` and handed to the model as an input. The
model's job is to explain and recommend, never to decide a credit rating. An
identical statement therefore always produces an identical rating, which is
what makes the decision reproducible and auditable.

## PDF ingestion

`pdf_parser.py` runs two independent extraction engines and keeps whichever
recovers more complete records.

**Engine 1 — Table Grid Parser.** Uses pdfplumber's table extraction and
handles 4-, 5- and 6-column layouts, including banks that split amounts across
separate DEPOSITS and WITHDRAWALS columns. Header variants (`particulars`,
`narrative`, `memo`, `chq`, …) are normalized onto canonical column names.

**Engine 2 — Date-Block Text Parser.** For borderless PDFs where no table grid
exists. Walks the page line by line, groups multi-line UPI/NEFT memos under
their leading date, and resolves each row's Credit/Debit direction in
preference order:

1. an explicit trailing `Credit`/`Debit`/`Cr`/`Dr` column token, if present
2. otherwise running-balance movement — a balance that rose by exactly the
   transaction amount is a credit, one that fell is a debit
3. otherwise conservative keyword inference, with product names such as
   "Credit Card Payment" explicitly excluded from counting as inflows

Both engines emit the same canonical schema: `date`, `description`, `amount`
(always positive), `type` (`Credit` / `Debit`).

## Privacy and prompt safety

Two guards sit between the customer's data and the OpenAI API.

`sanitizer.py` masks PII in every transaction description before it leaves the
process — bank account numbers, credit card numbers, phone numbers, email
addresses, PAN and SSN patterns.

`agent.py` encapsulates all untrusted input inside `<customer_metrics>` and
`<rag_context>` XML boundaries, and the system prompt instructs the model to
treat everything inside those tags as a data payload only — never as
instructions. This defends against indirect prompt injection through a crafted
transaction memo.

## How RAG works in this project

The `knowledge_base/` directory contains ten markdown files, one per banking
product: fixed deposit, recurring deposit, savings account, sweep account,
credit card, personal loan, home loan / mortgage, debt consolidation loan,
mutual funds / SIP, and SME credit line.

At startup, BankLens:

1. Loads all ten files and splits them into overlapping chunks with
   `RecursiveCharacterTextSplitter`, using markdown-header-aware separators
   (chunk_size=500, overlap=50)
2. Embeds each chunk with OpenAI `text-embedding-3-small` and stores the
   vectors in a persisted ChromaDB collection
3. Builds a BM25 lexical index over the same chunks and caches it in-process

When a statement is analyzed:

1. The computed metrics are rendered into a natural language query by
   `build_retrieval_query()` — defined once and shared by the app and the
   evaluation harness, so the evals measure the retrieval path that actually
   ships
2. The query runs against **both** indexes — dense semantic search catches
   conceptual matches, BM25 catches exact product terminology
3. The two ranked lists are merged by Reciprocal Rank Fusion, weighted 0.6
   dense to 0.4 sparse, producing `RETRIEVAL_CANDIDATE_K` candidates
4. A reranker narrows those candidates to the `RETRIEVAL_K` passages that
   reach the LLM
5. Retrieved chunks and their source filenames are passed to GPT-4o as
   grounded context; the model is instructed not to name any product outside
   that context, and the output guardrail enforces it
6. The UI displays which knowledge base files were used, making every
   recommendation traceable

The ChromaDB index persists to `./chroma_db/`. If a persisted index is found
but fails to load — a schema change after an upgrade, for example — `rag.py`
self-heals by discarding it and rebuilding from the knowledge base.

## Reranking

Fusion is cheap but coarse. Dense search scores the query against chunk
embeddings computed independently of one another, and BM25 scores term
overlap; neither ever considers the query and a passage *together*. A reranker
does, which is why retrieving wide and reranking narrow is usually the largest
quality gain available to a RAG system for the least code.

The gap is measurable. Scoring the lexical half alone against the golden
queries, with relevance labelled per risk band:

| BM25 only | hit | MRR | NDCG |
|---|---|---|---|
| top-4 | 0.677 | 0.238 | 0.244 |
| top-15 | 1.000 | 0.303 | 0.830 |

At the final cut of 4, roughly a third of queries surfaced no relevant product
document at all. Widened to 15, every query contained one. The right document
was being found and then discarded before the model saw it — which is exactly
what reranking recovers. Reproduce with `python -m evals.run_evals --headroom`;
it needs no API key.

Two backends, chosen by `RERANK_BACKEND`:

- **`llm`** (default) — one listwise call to `gpt-4o-mini`. No extra
  dependencies, reuses the existing key, about a second of added latency.
- **`cross_encoder`** — a local sentence-transformers cross-encoder. Lower
  latency and no API cost, but it pulls in torch: several hundred MB of image
  and more memory than the t2.micro this deploys to has spare. Opt-in, for
  larger hosts (`pip install sentence-transformers`).
- **`none`** — use the fusion order directly.

Reranking can never break retrieval. A missing key, an unknown backend name, an
absent dependency, a model error or a malformed response all fall back to the
fusion ordering and log the reason. A model that returns too few indices is
padded from the original order, because silently shrinking the context window
is a subtle way to lose grounding.

## How the LangChain agent works

`agent.py` builds an LCEL chain:

```
ChatPromptTemplate  →  ChatOpenAI (gpt-4o, temp=0.2)  →  PydanticOutputParser
                              ↓ with_fallbacks
                       ChatOpenAI (gpt-4o-mini)
```

The prompt combines a system message from `prompts/system_prompt.txt` (persona,
grounding rules, product strategy, tone), the customer's `FinancialMetrics` as
JSON, the reranked context with source filenames, the **already-computed risk
rating**, and Pydantic format instructions.

The schema is split in two, and the split is the point:

`ProfileNarrative` is what the model is asked to write.

| Field | Description |
|---|---|
| `financial_persona` | Short archetype label |
| `income_stability_analysis` | Income source and liquidity commentary |
| `spending_pattern_breakdown` | Essential vs discretionary split |
| `credit_risk_assessment` | Justification of the *assigned* rating |
| `primary_product` + `primary_reason` | Lead recommendation |
| `secondary_product` + `secondary_reason` | Cross-sell recommendation |
| `rm_hook_points` | Exactly three pitch bullets |

`CustomerProfile` extends it with fields the application owns.

| Field | Source |
|---|---|
| `financial_health_score` | Computed in `analyzer.py`, bounded 0–100 |
| `risk_profile` | Computed in `analyzer.py` |
| `retrieved_sources` | The files retrieval actually returned |

Because the risk rating is not a field on the schema the model receives, it
cannot set it — the guarantee is structural rather than a request in a prompt.

### Output guardrails

Pydantic validates *types*. It cannot know whether a string names a product the
bank sells, so `primary_product` and `secondary_product` are additionally
validated against a catalogue built from the knowledge base at runtime, matched
on token overlap against both the filename and the document's H1 title. Real
variants such as "High-Yield Savings Account" and "Sweep-In Fixed Deposit"
resolve; inventions such as "Platinum Rewards Card" are rejected.

Strict validation alone would be brittle, so a rejection triggers one
corrective retry with the validation error fed back to the model. If the retry
also fails, the request fails loudly rather than surfacing a product that does
not exist to a Relationship Manager.

The system prompt encodes three scenario playbooks — high saver, active
lifestyle spender, and cashflow stressed — including a **credit default
guardrail** that forbids recommending credit cards or unsecured debt to a
customer in genuine cashflow deficit. The guardrail keys on the computed
`is_cashflow_negative` flag rather than on an expense-ratio threshold: a
customer spending 87% of income is stretched but solvent, and treating them as
distressed both misreads the customer and collides with the active-spender
playbook.

## Evaluation

The suite lives in `evals/` and is split by what it costs to run, so the free
half can gate every push while the paid half stays occasional.

**Layer 1 — deterministic.** No API key, no network, 65 golden cases. It runs
inside the normal pytest job, so it gates every push at zero cost. Cases are
synthesized by rescaling consumption spending to hit a *target savings rate* —
exact, because `savings_rate_pct == 100 * (1 - expense_to_income_ratio)` — which
means the expected outcome can be written down by hand rather than recomputed
by the code under test. Expected risk bands live in an explicit literal table
in `evals/dataset.py`; that duplication is deliberate.

**Layer 2 — grounded.** Requires an API key, runs over a sampled subset.
Checks that recommended products exist, that the credit guardrail held, that
the recommended product's document was actually retrieved, and that quoted
percentages trace back to real metrics. An LLM judge on `gpt-4o-mini` — not the
model under test, to avoid self-preference bias — scores groundedness and
returns verbatim quotes of unsupported claims rather than a score out of ten.

```bash
python -m evals.run_evals                   # free
python -m evals.run_evals --headroom        # free, retrieval headroom
python -m evals.run_evals --retrieval-ab    # reranker A/B (needs a key)
python -m evals.run_evals --with-llm --judge
```

The harness was validated by mutation testing before being trusted: shifting
the risk boundary from 30 to 25 produced exactly the six failures that straddle
that range, breaking the health score's monotonicity was caught by an aggregate
property, and removing the Savings-transfer exclusion from expenses produced
twenty. A suite that has never been seen to fail is not evidence of anything.

## Running Tests

```bash
source .venv/bin/activate
pytest tests/ --cov=app --cov-report=term-missing -v
```

No API key is required — the whole suite runs offline.

It covers metric computation and its edge cases (zero income, single month),
risk banding and health score calibration, keyword and dataframe
categorization, PII masking, knowledge base loading and chunking, PDF parsing
including Credit/Debit inference, the output guardrails and their corrective
retry, reranker fallback behaviour, retrieval metrics, and layer 1 of the
evaluation suite over all 65 golden cases.

## Statement Format

**CSV** must carry these exact column names:

| Column | Type | Description |
|---|---|---|
| `date` | string | Transaction date (any parseable format) |
| `description` | string | Merchant name or memo |
| `amount` | float | Always positive |
| `type` | string | `Credit` or `Debit` |

## CI/CD Pipeline

```
Push to main
     │
     ▼
 Job 1: Lint          black --check  +  flake8
     │ pass
     ▼
 Job 2: Test          pytest tests/ --cov=app
     │ pass
     ▼
 Job 3: Build         docker build → docker push to ECR
     │ pass
     ▼
 Job 4: Deploy        SSH → docker pull → docker run
```

Pull requests trigger only Jobs 1 and 2. Jobs 3 and 4 run only on pushes to
`main`. The persisted ChromaDB volume survives deploys — `rag.py` rebuilds the
index automatically if it ever fails to load.

Job 2 already runs layer 1 of the evaluation suite, since it costs nothing.

### Evaluation Pipeline

`.github/workflows/eval.yml` runs the layer that costs money, deliberately kept
out of the deploy path so a README typo never spends OpenAI credits:

- **nightly** at 02:30 UTC
- **manually**, with a toggle for whether to include the LLM judge
- **on pushes to `main`** that touch `prompts/`, `app/pipeline/`,
  `knowledge_base/` or `evals/` — the paths that can actually change output
  quality

It reports the deterministic scorecard, retrieval headroom, the reranker A/B,
and grounded and judged results, and exits non-zero on a blocking failure.
