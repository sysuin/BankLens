# Responsible AI note — BankLens Platform

**Version** 1.0 · **Date** 2026-09-08 · **Owner** Sunny Singh · **Status** shipped with Phase 7

This note answers the questions a bank's model-risk or compliance reviewer
asks before an AI system touches customer data. Every claim points at a file
or a number in this repository; nothing here is aspirational.

## 1. What the system does, and what the model does not decide

BankLens reads a customer's bank statement and produces, for a relationship
manager (RM): computed financial metrics, a risk band, a product
recommendation grounded in the bank's own catalogue, and a tool-calling chat
over the statement. It also runs an **income-verification decision** that a
human reviewer approves or rejects.

The line between code and model is deliberate and enforced:

| Decided by code, never by a model | Written by a model, always validated |
|---|---|
| Income, expenses, savings rate, ratios (`app/pipeline/analyzer.py`) | The narrative explaining those numbers |
| Risk band and health score (fixed thresholds in `analyzer.py`) | The two product recommendations, validated against the catalogue |
| Declared vs observed income and whether a reviewer is needed (`app/graph/nodes.py`) | The RM's call hooks |
| Whether a question is answered from the warehouse (`app/warehouse/router.py`) | Free-form chat answers, after guardrails |

The output schema is split so the model **cannot** set the risk band: it is
not a field the model is asked for (`ProfileNarrative` vs `CustomerProfile` in
`app/pipeline/agent.py`).

## 2. Human oversight

- A discrepancy between declared and observed income above a threshold
  (20 %, `INCOME_REVIEW_THRESHOLD_PCT`) pauses the pipeline. No recommendation
  is written until a **reviewer** approves or rejects. The run is checkpointed
  and resumes from the decision (`app/graph/`).
- Reviewers and RMs are separate roles with separate powers, enforced in the
  API and in the database role the chat uses.
- Every node and every human action writes an append-only audit row: actor,
  inputs hash, model, prompt version, tokens, duration (`audit_events`).

## 3. Guardrails

Deterministic and applied before any model runs (`app/platform/guardrails.py`):

- The uploaded statement is treated as attacker-controlled text. Instruction-
  like descriptions are neutralised at ingest; amounts and dates are kept.
- Chat questions are checked for injection, then routed, then gated on scope
  by vocabulary coverage, then PII-redacted.
- Model output is scanned for echoed instructions and PII shapes.
- SQL is never generated by a model. The chat runs vetted templates as a
  database role that can read only tenant-filtered views.

The red-team suite (`make redteam`, 80 cases) runs on every push: block rate
100 % on attacks, 0 % false positives on benign inputs.

## 4. Fairness and bias

The metrics and the risk band are arithmetic over amounts and dates. They do
not read names, merchants' languages, or any demographic signal, and the bias
check proves it: `python -m evals.bias_check` rewrites every golden statement
with names and merchant spellings from different groups and asserts the risk
band and score are **identical** across variants, and that the guardrail
scan does not flag any group more than another. It runs in CI.

The model's narrative can still carry tone. It is validated for product
names and scanned for PII, and it never changes a number. Residual risk:
wording differences across groups in the narrative. Mitigation in place: the
narrative is shown to an RM, never to a customer, with the numbers beside it.

## 5. Data

See `docs/governance/DATA_RETENTION.md`. In one line: PII is masked before
any text leaves the bank's boundary, all demo data is synthetic, spans carry
ids and numbers only, and the audit trail records hashes of inputs rather
than the inputs.

## 6. Monitoring and cost

Every request, node, retrieval, model call and chat tool call is an
OpenTelemetry span with tokens and cost. Per-tenant daily budgets are
enforced from the same table tracing writes. The golden suite reports pass
rates, p50/p95/p99 latency and cost per query; `make compare` runs it on two
providers side by side (`docs/numbers_card.md`).

## 7. Known limitations (honest list)

- The categorizer's model fallback sends unmatched merchant descriptions to a
  hosted model unless the gateway is on the local provider.
- Vision OCR for scanned PDFs sends page images to a hosted model **before**
  masking. It is off by default and documented as a trade-off.
- LangGraph's checkpoint tables are not tenant-scoped; they are addressed by
  run id, which is reachable only through a row-level-secured table.
- The golden set covers the Meridian catalogue; the Harbor catalogue has
  fewer grounding checks (recorded as a finding in the numbers card).
- The local 3B model fails the advisory "quotes exact percentages" check on
  every golden case. It passes every blocking check.
- The rate limiter is in-process; a multi-process deployment needs Redis.

## 8. Incident response

Kill switches: `LLM_PROVIDER` to force the local provider, `TENANT_DAILY_
BUDGET_USD` to cap spend, `TRACING_ENABLED`, and `GUARDRAIL_INJECTION_
BLOCK_SCORE`. A misbehaving prompt is a versioned artefact: the registry
(`prompt_versions`) says which version ran against which model, and every
profile records its prompt version.
